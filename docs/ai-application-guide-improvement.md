# AI 신청 준비 가이드 — 실제 공고 기반 개선과 검증

1차 구현([ai-application-guide.md](ai-application-guide.md)) 이후, **실제 수집된 공고문으로 결과 품질을 검증**하며 고친 내용과 그 근거를 정리한다.
기능 설명은 위 문서에 있고, 이 문서는 **"왜 고쳤고 실제로 나아졌다는 근거가 무엇인가"** 를 담당한다.

---

## 1. 개선 배경

1차 구현은 "API가 동작한다"까지만 확인된 상태였다. 실제 공고문으로 검증해 보니 **동작은 하지만 결과가 틀리거나 비어 있는 경우**가 여럿 나왔다.

```
공고문을 못 찾음        LH 공고 일부가 파일이 있는데도 "찾지 못했어요"
입력이 잘림             100쪽 넘는 공고에서 자격·소득 영역이 통째로 빠짐
서류가 빠짐             조건부 제출서류가 입력에는 있는데 결과에 없음
안내가 틀림             읽을 수 없는 형식인데 "이미지 문서"라고 안내
```

공통점은 **사용자가 화면에서는 원인을 알 수 없다**는 것이다. 가이드가 비어 있거나 잘못돼도 "AI가 원래 그런가 보다"로 보인다. 그래서 각 사례를 `문제 → 원인 → 개선 → 검증` 순으로 끝까지 추적했다.

검증 원칙은 하나였다 — **AI 결과만 보고 판단하지 않는다.**

```
원문 PDF  ↔  Reducer가 Gemini에 보낸 내용  ↔  Gemini 결과
```
세 단계를 모두 대조해야 "프롬프트 문제"인지 "애초에 입력에 없었던 것"인지 갈린다. 실제로 **빠진 서류의 원인이 단계마다 달랐다.**

## 2. 최종 처리 흐름

```
관심 공고 저장 (없으면 서버가 403)
      ↓
캐시 확인  — prompt/reducer 버전 · 모델 · 프로필 수정시각이 모두 같으면 바로 반환
      ↓
공고문 찾기 (NoticeDocumentLocator)
      ├ ① notice_attachment 에서 찾기           SH · GH · GBDC
      └ ② 없으면 상세 페이지 폴백               LH · GBDC
         NoticeDocumentFallback 구현이 기관별 HTML 해석만 담당하고,
         이름 점수 · 형식 판정 · 정렬은 Locator 가 공용으로 처리한다
      ↓
텍스트 추출 (NoticeDocumentTextExtractor)
      ├ %PDF 매직바이트 검사 → 아니면 DOWNLOAD_FAILED
      ├ HWPX → UNSUPPORTED_DOCUMENT_FORMAT (내려받기 전에 중단)
      └ PDF 쪽 단위 / HWP 문단 단위
      ↓
영역 선별 (ApplicationSectionReducer)
      관련 영역은 평상시 전부 전달. 상한은 이상치에서만 작동
      ↓
Gemini → 출처 검증(Sanitizer) → DB 저장 → 화면
```

실패는 예외가 아니라 **화면이 그려야 할 상태**로 내려간다(`status: UNAVAILABLE` + `reason`). 어떤 경우에도 공고 원문 링크는 함께 내려간다.

## 3. 주요 개선 사항

| 영역 | 개선 |
| --- | --- |
| 입력 상한 | 정상 공고를 줄이는 cap → **이상치만 막는 비상 상한(150,000자)** |
| LH 공고문 탐색 | `입주자…모집` 계열 작명을 인식 — 실패 51/52 → **52/52** |
| 기관 확장 | 폴백을 전략 구조(`NoticeDocumentFallback`)로 분리하고 **GBDC 추가** |
| 형식 처리 | HWPX를 **지원하지 않는 형식으로 명시** (기존에는 "이미지 문서"로 오안내) |
| 잘못된 응답 방어 | `.pdf` 주소가 XML 오류를 돌려주는 경우 **`DOWNLOAD_FAILED`** 로 구분 |
| 첨부 유형 필터 | 수집기가 붙이는 부속자료 유형 4종을 제외 목록에 보강 |
| 프롬프트 v3 | 조건부 서류 누락 방지 / 불필요한 확인 항목 제거 |
| 화면 | 가이드 페이지 중앙 정렬 누락 수정 |

개선 후 확정된 버전·설정값은 다음과 같다. 저장된 결과를 재사용할지 판단하는 기준이기도 하다.

```
GuideVersions.PROMPT         application-guide-v3
GuideVersions.REDUCER        reducer-v3
emergency-max-input-chars    150000      ← 평상시 걸리지 않는 비상 상한
neighbor-pages               1
```

## 4. 대표 사례 — 문제 → 원인 → 개선 → 검증

### 4-1. 긴 공고문에서 입력이 잘리던 문제

**문제.** 108쪽짜리 GH 경기행복주택 공고에서 자격·소득기준 쪽이 통째로 빠졌다.

**원인.** `max-input-chars`(30,000)가 **원문 폭주를 막는 장치가 아니라, Reducer가 이미 "관련 있다"고 고른 내용을 다시 버리는 제한**으로 동작하고 있었다.

```
전체 202,887자
   ↓ 키워드 매칭        ← 폭주 방지는 사실상 여기서 끝난다
 matched 75,650자
   ↓ cap 30,000        ← 관련 있다고 판단한 것을 다시 60% 버린다
    29,964자 (관련 쪽 47개 중 18개)
```
게다가 예산 경계에서 **점수가 높은 큰 쪽이 점수 낮은 작은 쪽에 밀려나는** 역전까지 일어났다.

**개선.** 상한의 역할을 바꿨다. 관련 영역은 평상시 전부 보내고, 상한은 추출 오류·키워드 오탐 같은 **이상치에서만** 작동하게 했다. 설정 이름도 의미에 맞게 바꿨다(`emergency-max-input-chars`). 선택 우선순위(`영역별 핵심 → 점수순 → 앞뒤 문맥`)는 이미 올바라서 **알고리즘은 바꾸지 않았다.**

**검증.** 값을 임의로 고르지 않고, 수집된 공고를 **전수 측정**해 분포에서 정했다.

```
대상 98건 → 측정 성공 97건 (LH 52 · SH 43 · GH 2)
```

| metric | median | p90 | p95 | **max** |
| --- | ---: | ---: | ---: | ---: |
| PDF 쪽 수 | 23 | 46 | 51 | 108 |
| 전체 추출 글자 | 30,851 | 63,903 | 80,071 | 202,887 |
| **관련 영역 + 문맥 (실제 전송량)** | 30,789 | 59,971 | 70,006 | **92,297** |

```
최대 92,297자  →  150,000 은 그 1.63배
150K 에서 관련 영역이 잘린 공고 = 0 / 97건
100K · 200K · 250K 로 바꿔도 결과가 같다 (앞뒤 문맥이 ±1쪽이라 자연히 포화한다)
```

**실제 E2E (notice 109, 108쪽).**
```
원문 203,350자 → 전송 93,851자
input 65,754 tokens · output 2,035 · finishReason=STOP
Gemini 7,460ms
```
30,000에서 18개만 들어가던 관련 쪽이 **58개 전부** 들어갔고, 빠졌던 자격·소득 쪽이 결과에 반영됐다.

> 부수 확인 — **입력 크기는 응답 시간에 거의 영향이 없다.** 22,537자가 6,544ms, 93,851자가 7,460ms로 입력이 4.2배인데 14%만 늘었다. 응답 시간은 출력 길이가 지배한다. 토큰 비율은 실측 **0.70 토큰/자**.

### 4-2. LH 공고문을 찾지 못하던 문제

**문제.** LH 공고 일부에서 상세 페이지에 공고문 PDF가 멀쩡히 있는데도 `NO_DOCUMENT`가 났다.

```
20260922철원갈말영구임대예비입주자모집.pdf        (notice 34)
군산시국민임대입주자상시모집(경암부향등7개단지).pdf  (notice 40)
```

**원인.** 공고문 후보는 파일명에 `모집공고`·`공고문`·`공고` 같은 단서가 있어야 점수를 받는데, **두 파일 모두 '공고'라는 말이 한 번도 없다.** 점수 0 → 제외 → "찾지 못했다".

**개선.** `"모집"` 한 단어를 단서에 넣는 방법은 쓰지 않았다. 신청서·안내문·결과 명단에 너무 쉽게 들어가 부속자료가 공고문으로 승격된다. 대신 **`입주자`를 앵커로 요구하고 그 뒤 수식어 길이를 제한**했다.

```java
Pattern.compile("입주자[가-힣]{0,5}모집")
```

간격 5자는 임의로 정한 값이 아니다. **수집된 공고 97건의 제목·파일명에서 실제로 쓰인 수식어를 전부 세어** 정했다.

```
(없음) 107건   추가 7   상시 4   수시 4   최초 2   정례 2
격완화상시 2   자격완화 1   격완화추가 1   선착순상시 1      ← 최대 5자
```
수식어를 열거하는 방식도 시도했다가 버렸다. `최초`가 빠져 테스트가 깨졌고, 새 변형이 나올 때마다 또 누락될 구조였다. 반대로 `입주자.*모집`처럼 열어 두면 `입주자격 완화 안내 및 모집일정`(간격 6자) 같은 부속자료까지 걸린다.

**검증.**
```
LH 상세 페이지 52건 재판정 → 공고문 탐색 성공 51/52 → 52/52
이 규칙이 떠받치는 공고 4건 (notice 17 · 18 · 34 · 40)
  = 파일명에 '공고' 가 없어, 규칙이 없으면 전부 NO_DOCUMENT
```
notice 34·40 모두 실제 화면에서 가이드 생성까지 확인했다. PDF와 HWP가 함께 있을 때 **PDF가 선택**되는 것도 함께 확인했다(출처에 쪽수를 붙일 수 있다).

### 4-3. GBDC 공고에서 공고문을 아예 찾을 수 없던 문제

**문제.** 경상북도개발공사 공고가 모두 `NO_DOCUMENT`였다. 실제 사이트에는 모집공고 PDF가 있다.

**원인.** 마이홈 공공데이터 API는 **첨부파일 목록을 주지 않고**(상세 URL만 준다), 당시 GBDC 전용 수집기도 없었다. `notice_attachment`가 0행이라 찾을 것이 없었다.

**개선.** 두 갈래로 해결됐다.

- **수집기 쪽(PR #35)** — `GbdcHousingDetailSource`가 상세 페이지에서 첨부를 수집해 저장한다. 근본 해법이다.
- **조회 쪽(이번 작업)** — 기관별 폴백을 `NoticeDocumentFallback` 전략으로 분리하고 GBDC 구현을 추가했다.

둘은 중복이 아니라 **순서가 있다.** `Locator`가 DB를 먼저 보므로, 수집기가 공고문을 저장한 공고에서는 폴백이 아예 호출되지 않는다(HTTP 요청도 없다). 폴백은 **아직 재수집되지 않은 공고 · 수집 실패 · 첨부 누락** 때만 동작하는 안전망으로 남겼다.

**검증.** PR #35 적용 후 기존 공고를 재수집했다.

```
notice 58  첨부 6건 중 ANNOUNCEMENT PDF 1건
notice 60  첨부 5건 중 ANNOUNCEMENT PDF 1건
두 공고 모두 실제 화면에서 AI 가이드 생성 정상
```
주택목록(xlsx·pdf) · 평면도 · 제출서류 양식은 모두 후보에서 제외되고 모집공고 PDF가 선택됐다.

### 4-4. PDF가 아닌 응답을 PDF로 처리하던 문제

**문제.** GH 공고 하나(notice 111)에서 `.pdf` 주소가 **277바이트짜리 XML 오류를 HTTP 200으로** 돌려줬다.

```xml
<Root xmlns="http://www.nexacroplatform.com/platform/dataset">
  <Parameter id="ErrorCode" type="int">-1</Parameter>
```

**원인.** 그대로 PDF 파서에 넘기면 "파일을 읽지 못했습니다"(`EXTRACT_FAILED`)가 되는데, 실제 원인은 **다운로드 실패**다. 사용자에게 할 안내가 다르다.

**개선.** 내려받은 바이트가 `%PDF`로 시작하는지 검사해 `DOWNLOAD_FAILED`로 구분한다.

**검증 (notice 111 E2E).**
```
화면    "공고문 파일을 내려받지 못했어요." + 다시 시도 버튼
로그    noticeId=111, reason=DOWNLOAD_FAILED
Gemini  호출 0회 — 추출 단계에서 끝나 사용량을 쓰지 않는다
```

### 4-5. HWPX를 "이미지 문서"로 잘못 안내하던 문제

**문제.** HWPX만 첨부된 공고에서 "공고문이 이미지로 되어 있어 내용을 읽지 못했어요"가 떴다. 이미지 문서가 아니다.

**원인.** 쓰고 있는 Tika의 한글 파서는 **HWP v5만 지원**한다. HWPX는 zip 기반이라 전용 파서가 없어 텍스트가 제대로 나오지 않고, 글자 수가 적으면 스캔 문서로 오판된다.

**개선.** HWPX 전용 파서나 OCR을 넣지 않고 **지원하지 않는 형식으로 명시**했다.

```
UNSUPPORTED_DOCUMENT_FORMAT
"HWPX 형식의 모집공고문은 현재 AI 분석을 지원하지 않아요. 원문 공고문에서 내용을 확인해주세요."
```

후보 선정 단계에서 빼지 않은 것이 중요하다. 빼면 **파일이 있는데도 "찾지 못했다"** 가 되어 안내가 또 틀어진다. 대신 추출 단계에서 거부하고, 같은 공고에 PDF나 HWP가 있으면 **읽을 수 있는 쪽이 먼저 선택**되도록 형식 우선순위를 뒀다(PDF > HWP > HWPX).

### 4-6. 조건부 제출서류가 결과에서 빠지던 문제

**문제.** LH 매입임대 공고(notice 26, 17쪽)에서 제출서류 3종이 결과에 없었다.

```
배우자 주민등록표등본      (세대 분리된 경우에만 추가 제출)
임신진단서 / 입양관계증명서  (해당시 제출)
외국인등록증 사본          (외국인 배우자를 가구원에 포함하는 경우)
```

**원인 추적.** 단계별로 끊어 보니 **프롬프트 문제로 확정**됐다.

```
원문 7쪽에 존재          ✅
Extractor 가 추출        ✅
Reducer 가 7쪽을 선택    ✅
Gemini 입력에 포함       ✅
Gemini 결과에만 없음     ❌  ← 여기서만 사라진다
```
세 건의 공통점은 **조건이 서류 이름 칸이 아니라 옆 칸에 적힌 행**이라는 것이었다.

**개선 (프롬프트 v3, 한 번에 수정하고 버전 1회 증가).**
- 표의 행을 위에서 아래로 하나씩 확인하고, **조건이 옆 칸에 있어도 별개 서류로** 적을 것
- `personalChecks` 최소 개수 강제를 없앰 — 개수를 채우려 신청방법 같은 비개인화 항목이 들어왔다
- `NOT_APPLICABLE` 정의 확대 — 사용자가 '해당 없음'이라 명시한 계층을 다시 확인하게 하던 노이즈 제거

**검증 (notice 26).** 같은 공고를 v3로 재생성해 v2와 대조했다. **입력이 글자 단위로 동일**해(상한에 걸리지 않는 길이) 차이가 전부 프롬프트 효과로 귀속되는 깨끗한 비교였다.

```
notice 26 (LH 매입임대 17쪽)   v2 → v3
제출서류  9건 → 13건   (원문 7·8쪽 표의 모든 행을 덮음, 환각 0건)
  빠졌던 조건부 3종 전부 복구
  원문에 있던 대리 신청 서류도 새로 포착
확인사항  3건 → 2건   (신청방법 항목이 사라지고 실제 대조 가능한 것만 남음)

출처                 신규 항목 전부 정확 (물리 쪽 = 인쇄 쪽, offset 0 확인)
```

## 6. 오류 처리 정책

가이드를 못 만든 것은 장애가 아니라 **화면 상태**다. HTTP 오류로 내리지 않고 `reason`으로 구분한다.

| reason | 화면 문구 | 다시 시도 | Gemini |
| --- | --- | :---: | :---: |
| `NO_DOCUMENT` | 분석할 수 있는 모집공고 파일을 찾지 못했어요 | ✕ | 0회 |
| `UNSUPPORTED_DOCUMENT_FORMAT` | HWPX 형식은 현재 AI 분석을 지원하지 않아요 | ✕ | 0회 |
| `SCANNED_DOCUMENT` | 공고문이 이미지로 되어 있어 내용을 읽지 못했어요 | ✕ | 0회 |
| `DOWNLOAD_FAILED` | 공고문 파일을 내려받지 못했어요 | ○ | 0회 |
| `EXTRACT_FAILED` | 공고문 파일을 읽지 못했어요 | ○ | 0회 |
| `NO_RELEVANT_SECTION` | 공고문에서 신청 준비 관련 내용을 찾지 못했어요 | ○ | 0회 |
| `AI_NOT_CONFIGURED` | AI 기능이 아직 준비되지 않았어요 | ○ | 0회 |
| `QUOTA_EXCEEDED` | 오늘 사용할 수 있는 AI 분석 횟수를 모두 썼어요 | ○ | — |
| `AI_FAILED` | AI 분석에 실패했어요 | ○ | — |

두 가지가 일관되게 지켜진다.

- **결과를 만들 수 없다고 판단되면 Gemini를 부르기 전에 끝낸다.** 사용량을 쓰지 않는다.
- **어떤 상태에서도 공고 원문 링크는 내려간다.** AI가 실패해도 사용자는 원문으로 갈 수 있다.

고칠 수 있지만 **이번 범위에서 일부러 하지 않은** 것들이다. 각각 근거 데이터가 있으니 다음에 손댈 때 출발점으로 쓰면 된다.

| 항목 | 현재 상태와 근거 |
| --- | --- |
| **Reducer 키워드 정밀도** | 108쪽 공고 기준 관련 영역의 약 16.5%가 약한 매칭이다. 대피공간 설명·법조문·붙임 서식 머리말이 `증명서`·`무효`·`안내사항` 같은 넓은 키워드 하나로 걸린다. 입력 상한을 올리면서 이 양도 함께 늘었다. **상한 문제가 아니라 키워드 문제**라 분리했다 |
| **프롬프트 v4** | 아래 두 항목을 한 번에 처리하는 것이 캐시 비용상 유리하다. 프롬프트 버전을 올리면 저장된 결과가 전건 무효화된다 |
| **COMMON / CONDITIONAL 분류** | 원문이 "공통 제출서류" 표 안에 조건부 행을 섞어 두는 경우가 있다. 현재는 원문의 절 구분을 따르는데, 그러면 화면의 "모든 신청자가 내는 서류"라는 설명이 일부 항목에서 사실과 달라진다. **원문 표기 대신 실제 제출 조건을 기준으로** 바꾸는 방향을 검토 중이다 |
| **일부 조건부 서류 누락** | v3로 대부분 복구됐지만, 방문신청만 가능한 공고에서 '본인 신분증·도장'처럼 **조건이 붙지 않은 기본 행**이 묶여 흘러가는 경우가 남아 있다 |
| **JPDC / GMCC 폴백** | 제주개발공사는 첨부가 ZIP 하나뿐이라 압축 해제가 필요하고, 광주도시공사는 TLS 인증서 체인 확인이 선행이다. 두 기관 합쳐 공고 2건이라 우선순위를 낮췄다. **SSL 검증을 끄는 방식은 쓰지 않는다** |

## 8. 운영 / 개발 참고

### Gemini API 키와 quota는 세 기능이 공유한다

현재 `GEMINI_API_KEY` 하나를 **AI 신청 준비 가이드 · 공고 PDF 파서 · 공고 정규화**가 함께 쓴다. 기능별 정책(모델·타임아웃·호출 상한)은 각자 분리돼 있지만, **Google 프로젝트의 RPM / TPM / RPD는 공유된다.**

```
gemini.api.key / base-url        공통 — 이것만 공유한다
zipick.application-guide.*       AI 신청 준비 가이드 정책
zipick.gemini-pdf-parser.*       공고 PDF 파서 정책
zipick.gemini-normalization.*    공고 정규화 정책
```

- `APPLICATION_GUIDE_DAILY_CALL_BUDGET`(기본 200)은 **이 기능 자체의 보호장치**이고 Google quota와 별개다.
- 다른 기능이 대량 호출 중이면 사용자가 가이드를 눌렀을 때 `QUOTA_EXCEEDED`가 날 수 있다. **원인이 다른 기능일 수 있다.**
- 장문 공고 1건이 프로젝트 분당 입력 토큰의 상당 부분을 쓴다(108쪽 기준 약 66,000 tokens).

### 모델 환경변수의 적용 범위

```
APPLICATION_GUIDE_MODEL   AI 신청 준비 가이드 전용
GEMINI_MODEL              AI 신청 준비 가이드의 2순위 기본값 — 이 기능에만 적용된다
GEMINI_PDF_PARSER_MODEL   공고 PDF 파서 전용
```

> ⚠️ `GEMINI_MODEL`은 **팀 전체 공통 모델이 아니다.** AI 신청 준비 가이드만 이 값을 읽는다. 공고 PDF 파서는 `GEMINI_PDF_PARSER_MODEL`을, 정규화는 자체 설정값을 쓴다. 모든 AI 기능의 모델을 한 번에 바꾸는 환경변수는 없다.

### 수집 경로의 Gemini는 기본적으로 꺼져 있다

공고 수집을 로컬에서 돌릴 때 참고한다. 둘 다 기본값이 `false`이고, 켜면 수집 중 Gemini를 호출해 **가이드와 같은 quota를 쓴다.**

```
GEMINI_PDF_PARSER_ENABLED      기본 false
GEMINI_NORMALIZATION_ENABLED   기본 false
```

### 입력 상한은 평상시 걸리지 않는 값이다

`emergency-max-input-chars: 150000`은 **목표치가 아니라 이상치 차단선**이다. 측정된 97건 중 가장 큰 공고도 92,297자에서 멈춘다(앞뒤 문맥이 ±1쪽이라 자연히 포화한다).

낮추면 정상적인 긴 공고에서 자격·서류 정보가 잘리므로 **토큰을 아끼려고 내리지 않는다.** 혹시 이 값에 걸리는 공고가 생기면 축약 로그에서 바로 드러난다.

```
공고문 축약 완료: ... 덩어리 X/Y개      ← X 가 관련 영역 수보다 작으면 상한이 걸린 것
```

### 캐시 무효화 기준

저장된 결과는 **프롬프트 버전 · 선별 규칙 버전 · 모델 · 프로필 수정시각**이 모두 같을 때만 재사용한다. 프롬프트나 선별 규칙을 고치면 전건이 다시 만들어지므로, **검증용 캐시를 쓰는 작업이 남아 있다면 버전 변경을 마지막에 모아서** 하는 편이 호출 수를 아낀다.
